Five things worth recording, each found by writing the code rather than by
re-reading the plan:

1. **The plan's `V13` number was already taken** by Task 2's
   `policy_qa_answer`. The proposal table is `V14`.
2. **Supersession was impossible as the schema stood**, and that turned out
   to be a real design decision rather than an implementation detail — the
   seeded `SNAP-FY2026` set is open-ended and `V3`'s trigger refused every
   UPDATE, so a new set would overlap it and `findEffectiveOn` would throw
   on the next *determination*. Routed through the design-doc process at
   the user's direction: `docs/design/2026-08-23-policy-parameter-supersession.md`.
3. **One immutability function per table, not one shared function.** V3
   pointed both triggers at a single function; narrowing it broke
   `policy_parameter` with `record "old" has no field "effective_to"`,
   because PL/pgSQL plans a whole boolean expression up front rather than
   short-circuiting it — a `tg_table_name` guard does not help. Found by
   running the test, not by reading the SQL.
4. **The model omitted `household_size` and every size-scoped figure
   silently became scalar.** Fixed structurally by making the field
   *required* in the model-facing schema (no Python default, so the
   constrained decoder must emit it) and by writing the prompt's parameter
   list in the shape of the JSON rather than as prose. Then a second, more
   interesting failure: once the prompt taught the model that "sizes one
   through three" covers each size in the range, it correctly proposed
   sizes 2 and 3 — and the *test fixture* was wrong, having supplied only
   size 1. Measured 5/5 on the corrected, harder test.
5. **A test that passed alone and failed in the suite.** The negative-value
   test asserted `policy_parameter_proposal` was empty; the controller test
   commits its own rows into the same JVM-wide container. Re-asserted as a
   delta. Exactly what the whole-suite-every-time policy exists to catch.
6. **Ollama was silently truncating prompts — including Task 2's.** The
   most serious finding, and it was not visible from any test. `num_ctx`
   was never set, so it defaulted to 2048. Measured against the live
   model: the rule-authoring prompt for the *real* 39-parameter FY2026 set
   plus an 8,000-character excerpt is 12,186 characters, and Ollama
   reported `prompt_eval_count` of **1,026 at num_ctx=2048 versus 3,105 at
   4,096** — it discarded two thirds of the prompt and still answered
   `200 OK`. The parameter list sits at the front of that prompt, so the
   copilot would have been diffing against a list it never saw and
   proposing figures that look entirely plausible. Task 2's denial prompt
   measured 1,849 tokens against the same 2,048 ceiling — not yet
   truncating, but with no margin, which plausibly contributed to the
   uncited-answer flakiness recorded in the rows below. Fixed three ways:
   `num_ctx` is now explicit and settings-driven (4,096); `OllamaClient`
   refuses a prompt that would not fit rather than letting it be truncated
   (checked *before* the request — `prompt_eval_count` cannot detect this
   after the fact, since prompt caching lowers it too, making the two
   indistinguishable); and the excerpt cap came down from a guessed 8,000
   characters to a measured 6,000, leaving real headroom. Cost is roughly
   235MB more KV cache, which is the right trade against a wrong benefit
   figure.

| An infrastructure failure is currently indistinguishable from a genuine abstention | **Yes, for trust -- no, for shipping Phase 2.** Not a regression and not blocking Task 3, but it undermines the one guarantee the abstention path exists to give | Found 2026-08-23 while diagnosing a real `e2e` failure (`dfe2da7`, and again locally). When Ollama's `llama-server` is OOM-killed mid-run, the next generation comes back uncited; `service.py`'s grounding retry fires, also comes back uncited, and the system abstains -- writing an `ai.policy_qa_answer` row that says "insufficient information in the policy corpus to answer this". That row asserts something false *about the corpus* when the actual cause was the inference process dying. Design doc §2.2's abstention is an epistemic claim ("the corpus can't support an answer"), so silently overloading it with "the infrastructure broke" is a real correctness bug in a trust-critical path, and it also makes the failure undiagnosable after the fact.
